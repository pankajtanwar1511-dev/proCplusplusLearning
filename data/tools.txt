● Great question! Yes, AddressSanitizer is that easy, but let me give you the complete picture of all debugging tools and when to use each.

  1. AddressSanitizer (ASan) - Your Command Is Good!

  # ✅ Your command is perfect for development
  g++ -std=c++20 -O2 -g \
      -Wall -Wextra -Wpedantic -Werror \
      -fsanitize=address,undefined \
      -fno-omit-frame-pointer \
      program.cpp

  ./a.out  # Just run it - errors reported automatically

  What You Get:

  - Heap buffer overflow detection
  - Stack buffer overflow detection
  - Use-after-free detection
  - Use-after-return detection
  - Memory leaks (on exit)
  - Undefined behavior (from UBSan you added)

  Performance Cost:

  - ~2x slowdown (very reasonable for testing)
  - 2-3x memory overhead

  Example Output:

  int main() {
      int* arr = new int[5];
      arr[10] = 42;  // ❌ Heap buffer overflow
      delete[] arr;
  }

  =================================================================
  ==12345==ERROR: AddressSanitizer: heap-buffer-overflow on address 0x603000000068
  WRITE of size 4 at 0x603000000068 thread T0
      #0 0x4012ab in main program.cpp:3
      #1 0x7f8b1234abcd in __libc_start_main

  0x603000000068 is located 28 bytes to the right of 20-byte region
  allocated by thread T0 here:
      #0 0x4567ef in operator new[](unsigned long)
      #1 0x4012a3 in main program.cpp:2
  =================================================================

  2. All the Sanitizers Compared

  2.1 UndefinedBehaviorSanitizer (UBSan)

  # Already in your command! -fsanitize=undefined
  g++ -fsanitize=undefined program.cpp

  Detects:
  - Signed integer overflow
  - Division by zero
  - Null pointer dereference
  - Misaligned pointers
  - Invalid enum values
  - Array bounds (runtime-checked)

  int main() {
      int x = INT_MAX;
      x = x + 1;  // ❌ UBSan detects signed overflow

      int* p = nullptr;
      *p = 42;    // ❌ UBSan detects null dereference
  }

  Output:
  program.cpp:2:9: runtime error: signed integer overflow: 2147483647 + 1 cannot be represented in type 'int'
  program.cpp:5:5: runtime error: store to null pointer of type 'int'

  2.2 ThreadSanitizer (TSan)

  # For data races in multithreaded code
  g++ -fsanitize=thread -g program.cpp

  Detects:
  - Data races
  - Deadlocks (limited)

  ⚠️ Cannot combine with ASan! (Choose one)

  int shared = 0;

  void thread1() { shared = 1; }  // ❌ Data race
  void thread2() { shared = 2; }  // ❌ Data race

  int main() {
      std::thread t1(thread1);
      std::thread t2(thread2);
      t1.join(); t2.join();
  }

  2.3 MemorySanitizer (MSan)

  # For uninitialized memory reads
  g++ -fsanitize=memory -g program.cpp

  Detects:
  - Reads of uninitialized memory

  ⚠️ Requires rebuilding ALL libraries (hard to use)

  int main() {
      int x;
      if (x > 0) { }  // ❌ MSan detects uninitialized read
  }

  2.4 LeakSanitizer (LSan)

  # Included with ASan automatically, or standalone:
  g++ -fsanitize=leak program.cpp

  Detects:
  - Memory leaks

  int main() {
      int* p = new int(42);
      // Missing delete
  }  // ❌ LSan reports leak

  Output:
  =================================================================
  ==12345==ERROR: LeakSanitizer: detected memory leaks

  Direct leak of 4 byte(s) in 1 object(s) allocated from:
      #0 0x456789 in operator new(unsigned long)
      #1 0x401234 in main program.cpp:2
  =================================================================

  3. Valgrind (Different Approach)

  Valgrind Memcheck

  # Compile with debug symbols (NO sanitizer flags!)
  g++ -g -O1 program.cpp

  # Run under Valgrind
  valgrind --leak-check=full \
           --show-leak-kinds=all \
           --track-origins=yes \
           --verbose \
           ./a.out

  Valgrind vs ASan

  | Feature         | ASan                     | Valgrind                      |
  |-----------------|--------------------------|-------------------------------|
  | Speed           | ~2x slower               | ~10-50x slower                |
  | Recompile?      | ✅ Yes                    | ❌ No (binary instrumentation) |
  | Detection       | Heap/stack overflow, UAF | Same + uninitialized reads    |
  | Platforms       | Linux, macOS, Windows    | Mainly Linux                  |
  | False positives | Very few                 | Some                          |
  | Container-aware | Better                   | Limited                       |

  When to Use Valgrind:

  # ✅ Use Valgrind when:
  # - You don't have source code
  # - Testing third-party binaries
  # - Need to check system libraries
  # - Want uninitialized memory detection (without MSan complexity)

  valgrind --tool=memcheck ./third_party_binary

  # ✅ Use Valgrind's other tools:
  valgrind --tool=cachegrind ./a.out    # Cache profiling
  valgrind --tool=callgrind ./a.out     # Call graph profiling
  valgrind --tool=helgrind ./a.out      # Thread error detection

  4. Core Dumps (Post-Mortem Debugging)

  Enable Core Dumps:

  # Check current limit
  ulimit -c
  # unlimited or 0

  # Enable unlimited core dumps
  ulimit -c unlimited

  # Set core dump pattern (Linux)
  echo "core.%e.%p" | sudo tee /proc/sys/kernel/core_pattern
  # %e = executable name, %p = PID

  Generate and Analyze:

  // crash.cpp
  int main() {
      int* p = nullptr;
      *p = 42;  // Segfault → core dump
  }

  g++ -g crash.cpp
  ./a.out
  # Segmentation fault (core dumped)

  # Analyze with GDB
  gdb ./a.out core.a.out.12345

  (gdb) bt              # Backtrace
  (gdb) info registers  # Register state
  (gdb) x/10i $rip      # Disassemble around crash
  (gdb) print p         # Examine variables

  When to Use Core Dumps:

  ✅ Production crashes (save state for later analysis)✅ Difficult-to-reproduce bugs (one chance to capture)✅ Post-mortem analysis (no rerun needed)

● Great question! Here's how to integrate sanitizers and debugging tools with your colcon workflow for ROS 2:

  1. AddressSanitizer + UBSan with Colcon

  Development Build (Recommended):

  # Build with ASan + UBSan
  colcon build --symlink-install \
      --cmake-args \
          -DCMAKE_BUILD_TYPE=RelWithDebInfo \
          -DCMAKE_CXX_FLAGS="-fsanitize=address,undefined -fno-omit-frame-pointer -g" \
          -DCMAKE_C_FLAGS="-fsanitize=address,undefined -fno-omit-frame-pointer -g" \
          -DCMAKE_EXE_LINKER_FLAGS="-fsanitize=address,undefined" \
          -DCMAKE_SHARED_LINKER_FLAGS="-fsanitize=address,undefined" \
      --parallel-workers 4

  # Run your nodes
  source install/setup.bash
  ros2 run your_package your_node
  # Errors printed automatically to stderr

  Why RelWithDebInfo instead of Release?

  - Release: -O3 optimization, no debug symbols
  - RelWithDebInfo: -O2 optimization + debug symbols (-g)
  - Debug: -O0 (no optimization) + debug symbols

  For sanitizers, you want optimizations (find real bugs) + debug symbols (readable stack traces).

  2. ThreadSanitizer (for Multithreaded ROS Nodes)

  8. CMakeLists.txt Approach (Package-Specific)

  If you want sanitizers only for specific packages, modify their CMakeLists.txt:

  # In your_package/CMakeLists.txt

  cmake_minimum_required(VERSION 3.8)
  project(your_package)

  # Default to C++17
  if(NOT CMAKE_CXX_STANDARD)
    set(CMAKE_CXX_STANDARD 17)
  endif()

  # Compiler warnings
  if(CMAKE_COMPILER_IS_GNUCXX OR CMAKE_CXX_COMPILER_ID MATCHES "Clang")
    add_compile_options(-Wall -Wextra -Wpedantic)
  endif()

  # Optional: Add sanitizers via CMake option
  option(ENABLE_ASAN "Enable AddressSanitizer" OFF)
  option(ENABLE_TSAN "Enable ThreadSanitizer" OFF)

  if(ENABLE_ASAN)
    add_compile_options(-fsanitize=address,undefined -fno-omit-frame-pointer -g)
    add_link_options(-fsanitize=address,undefined)
    message(STATUS "AddressSanitizer enabled for ${PROJECT_NAME}")
  endif()

  if(ENABLE_TSAN)
    add_compile_options(-fsanitize=thread -fno-omit-frame-pointer -g)
    add_link_options(-fsanitize=thread)
    message(STATUS "ThreadSanitizer enabled for ${PROJECT_NAME}")
  endif()

  # ... rest of CMakeLists.txt
