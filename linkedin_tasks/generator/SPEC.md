# LinkedIn post spec format

One JSON file per topic in `posts/<chapter>/specs/`, holding a list of posts.
Render with:

```bash
cd linkedin_tasks/generator
python3 render.py ../posts/ch4_concurrency/specs ../posts/ch4_concurrency/out [POST_ID ...]
python3 build_queue.py ../posts/ch4_concurrency      # posting order (queue.json); dates come from ../bot/series.py
```

Posting, schedule and adding chapters to the series: `../bot/README.md`.

Full working examples: `examples/examples.json` (code puzzle, side-by-side puzzle, concept question, theory carousel).

## Post object

| Field | Meaning |
|---|---|
| `id` | `T06-TH` (theory), `T06-P6` (practice task 6), `T06-Q14` (interview question 14). Numbers are the source numbers in the topic files |
| `type` | `theory`, `code_puzzle` or `concept` |
| `topic_no`, `topic_short` | `6`, `"Memory Ordering"` (short name shown in slide footers) |
| `source` | e.g. `"topic_06 practice Q6"` |
| `text.hook` | First lines of the post, visible before "...see more". Max ~210 characters, 2-4 short lines. Ends with the call to action (work it out / pick / comment your answer, then swipe). Never "guess": address readers as engineers who can reason it out |
| `text.body` | Shown after "...see more". 1-4 short lines. Never gives away the answer |
| `text.hashtags` | 4-6 tags without `#` |
| `first_comment`, `bonus_answer` | Not used any more (kept from earlier drafts). The first comment is generic, generated by `comments.py` per post type |
| `slides` | List of slide objects (below) |

## Slide layouts

Every slide may have `cta` (footer text, e.g. "Swipe ➜"). Text fields accept `` `code` ``, `**bold**`, `*italic*`, `<br>`.

| `layout` | Fields | Used for |
|---|---|---|
| `puzzle` | `kicker`, `title`, `code` and/or `shared_code` + `columns` [`{label, code}`], optional `options` [strings, max 4, short] | Slide 1 of a code puzzle |
| `question` | `kicker`, `title`, optional `code`, `options` [4 strings] | Slide 1 of a concept question |
| `answer` | `verdict`, `verdict_sub`, optional `text`, `bullets` [≤4], optional `code`, optional `wrong` | Answer slide |
| `code` | `kicker`, `title`, `code` or `columns` [`{label, code, verdict, verdict_ok}`], optional `bullets`, `tip`, `takeaway` | Fix / twist / comparison slide |
| `wrong_options` | `items` [≤3], `takeaway` | Why the other options are wrong |
| `cover` | `kicker`, `hero`, `lead` | Theory slide 1 |
| `cards` | `kicker`, `title`, `cards` [`{label, text}`, ≤3], `takeaway` | Two or three concepts |
| `table` | `kicker`, `title`, optional `header`, `rows` [[a, b], ≤4], `takeaway` | Comparisons |
| `chain` | `kicker`, `title`, `steps` [≤4] | Step sequences (last step green) |
| `statement` | `kicker`, `hero`, `lead` | One big idea |
| `checklist` | `kicker`, `title`, `items` [≤5], optional `code`, `warn`, `takeaway` | Lists |
| `myths` | `title` (default "Answers that fail interviews"), `items` [`{myth, truth}`, 3] | Myth slides |
| `takeaway` | `hero`, `lead` | Final slide |

## Fit rules

- Slides are 1080x1080 squares: on the LinkedIn mobile feed a square page shows nearly full width, with only a sliver of the next page.
- The next-page sliver (~10%) falls inside the 72px left margin, so it never reveals the answer. An optional automatic "Lock in your answer" pause page exists (`AUTO_PAUSE_PAGE` in render.py, off by default).
- The renderer shrinks code first, then the whole slide, and reports overflow, code < 28px and text shrunk below 82% (`SMALL TEXT`).
- Keep code on a slide to about 16 lines; use `columns` for two-thread code and before/after comparisons.
- Aim for zoom 1.0 on text slides: if the report shows zoom below ~0.9, shorten the text.
- Code must render at 28px or more (phone readability); the renderer reports smaller code as a problem. Fix by shortening lines (aim ≤ 46 characters), using `columns`, moving comments into bullets, or splitting code over two slides.
